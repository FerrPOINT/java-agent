# Хранение состояния Java Agent

Metadata вложений находится в PostgreSQL, содержимое файлов — в
`agent.attachments.cache-root`. Для восстановления нужны обе части.
Профили, выбранный профиль и связанные файлы находятся в корне ProfileService.
Рабочий каталог агента имеет отдельный жизненный цикл.

## Настройки и владельцы

Источники значений: [application.yml](../../backend/src/main/resources/application.yml),
[ProfileService](../../backend/src/main/java/com/azhukov/agent/service/ProfileService.java)
и конкретный Compose/release manifest. Полный перечень томов установки
формирует deployment-адаптер из этих manifests.

| Настройка | Поведение |
| --- | --- |
| `HERMES_HOME` | Контейнерные конфигурации используют `/home/agent/.java-agent` на state volume |
| `AGENT_PROFILE_BASE_DIR` | Явный путь сохраняет приоритет; его родитель определяет корень состояния |
| `AGENT_ATTACHMENTS_CACHE_ROOT` | Связан с `agent.attachments.cache-root`; прямой property/JVM override сохраняется |
| `AGENT_CORE_WORKING_DIRECTORY` | Рабочие файлы находятся на отдельном `/workspace` |

Standalone Compose-конфигурации сохраняют существующий постоянный `/artifacts`
для вложений. State volume добавляется отдельно; очистка workspace не должна
удалять профили. E2E-конфигурация использует `attachments` внутри state root.
PVC, StorageClass, проверка прав и перенос Kubernetes принадлежат Base и infra.

Для самостоятельного JVM-запуска defaults не меняются: без явных настроек
ProfileService использует прежний `.hermes` внутри `user.home`, cache вложений —
`agent-attachments` внутри `java.io.tmpdir`. Долговременный пользовательский каталог
нужно выбрать явно. После ошибки доступа другой каталог не выбирается.

## Права и пути

Новые контейнерные state directories принадлежат `10001:10001`. Корень
образа ограничен режимом `0700`; существующий volume сохраняет свои данные
и требует отдельной проверки перед подключением.

На POSIX новые каталоги вложений создаются с `0700`, файлы — с `0600`.
Проверяется поддержка POSIX прав фактической файловой системой. В остальных
случаях действуют права этой файловой системы и родительского каталога.

Явно заданный cache root может быть файловым alias: приложение фиксирует
его реальный путь. Абсолютный artifact cache path, переход `..` и symlink
в относительном пути вложения отклоняются. Обычные вложенные пути и имена
с несколькими точками остаются допустимыми.

Регистрация следует после записи файла и сохранения metadata. Для duplicate
проверяются доступность, размер и SHA256 существующего blob. Недоступный каталог,
ошибка записи или отсутствующий duplicate blob возвращают отказ;
metadata автоматически не удаляется.

## Обновление существующей установки

До остановки старого контейнера deployment-оператор обязан:

1. Определить эффективные каталоги по env, JVM/system properties, Spring overrides
   и текущему image. Каталог из нового manifest не определяет старый источник.
2. Закрыть новые изменяющие запросы и проверить отсутствие активной работы.
3. Согласованно сохранить профили, вложения, связанные файлы и metadata.
   Копию writable layer получить до удаления старого контейнера/Pod.
4. Перенести данные с сохранением относительных cache paths и проверить SHA256,
   количество файлов, UID/GID и права. Пустой и отсутствующий каталоги допустимы.
5. При конфликте, неизвестном формате или metadata без blob остановиться.
   Исходную копию сохранить до приёмки. Массовый `chown` действующих томов
   и удаление записей БД не исправляют такое расхождение.

Прямое пересоздание старого Pod до capture уничтожает его writable layer.
Backup с остановкой writers нельзя использовать как первый шаг такой установки
без отдельной подготовки старого Java state.

Откат image сохраняет новый state mount и его конфигурацию. Профили и вложения
обратно в writable layer не возвращаются. Данные, принятые после rollout,
нельзя перезаписывать старой резервной копией.

## Проверка и срок хранения

После записи сохранить ID и SHA256 вложения, содержимое default/именованного
профиля и выбранный профиль. Проверить чтение после нового JVM-процесса,
пересоздания контейнера и замены Pod с новым UID. Compose и Kubernetes
проверяются отдельно на одном immutable image.

Постоянный том не отменяет прикладную очистку. Default TTL вложения —
86400 секунд; просроченные вложения и удалённые сессии очищаются по прежним правилам.
Для restart-проверок нужны неистёкшие данные, для TTL — отдельные фикстуры.
Сохранность workspace не означает автоматического продолжения прерванного
процесса или разрешения повторить его внешние действия.
